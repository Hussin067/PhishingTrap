# Phase 6 — Adaptive AI: behaviour analysis, prediction and agent

Status: **implemented and tested (55 automated tests). The ML component is experimental.**
All model results below come from SYNTHETIC data generated by our own rules and do **not** show real-world accuracy.

## 1. Architecture

```
Database (memory)  ──►  backend/app/services/behavior_service.py  ──►  ai/features.py (analysis)
                                                                          │
                                         ai/prediction_service.py (Random Forest tool)
                                                                          │
                                  ai/vulnerability.py  ──►  ai/agent.py (decision / orchestration)
                                                                          │  proposal only
backend/app/routers/adaptive.py  ◄── validates, asks for confirmation ────┘
        │
        └─► backend/app/services/adaptive_service.py  ──►  Simulation / Event / Training tables
```

| Component | Responsibility | Files |
|---|---|---|
| Database | Source of truth for recorded behaviour | `database/` (unchanged schema) |
| Behaviour service | The only code that reads behaviour data for the AI | `backend/app/services/behavior_service.py` |
| Feature engineering | Pure functions turning history into features (shared by training and live use) | `ai/features.py`, `ai/feature_engineering.py` |
| Random Forest | Estimates click probability (experimental tool) | `ai/model_config.py`, `ai/train_model.py`, `ai/prediction_service.py` |
| Vulnerability analysis | Per-scenario evidence, smoothed rate, interval, optional ML estimate | `ai/vulnerability.py` |
| Agent | Chooses next simulation, difficulty, training; explains itself | `ai/agent.py` |
| Simulation engine | Existing: templates, preview, click tracking | `backend/app/main.py`, `backend/app/templates/` |
| Training engine | Existing `Training`/`TrainingQuestion` tables; content in `training_catalog.py` | `backend/app/services/` |

Rules the design enforces: the `ai/` package never imports SQLAlchemy or `backend`; the agent has no side effects; the backend validates and executes only after explicit confirmation.

## 2. Data generation (synthetic)

`python -m ai.data_generation.generate_training_data`

* Campaign `ML Synthetic Training Dataset v1`; 12 employees x 200 simulations = 2,400 rows.
* Each employee has a baseline click probability plus scenario-specific increases (profiles in the script).
* Only simulations and events of that campaign are deleted before regeneration. Employees, other campaigns and trainings are untouched.
* The backend **excludes** this campaign from agent/analysis queries by default (`include_synthetic=false`); responses state their `data_source`.

## 3. Features (`ai/features.py`)

Computed from simulations **before** the one being predicted (no target leakage). Model inputs:

`phishing_type`, `total_simulations`, `total_clicks`, `total_reports`, `total_ignored`, `click_rate`, `report_rate`, `ignore_rate`, `recent_failures` (clicks in last 5), `scenario_attempts`, `scenario_clicks`, `scenario_click_rate`.

The CSV also contains `recent_click_rate`, `recent_report_rate`, further scenario rates, the identifiers and both targets; the identifiers and targets are never model inputs. `ai/feature_engineering.py` and the backend use the same functions (verified: the regenerated CSV was identical to the one produced before the refactor).

## 4. Model training and evaluation

Train: `python -m ai.train_model` (fits on all rows; writes `ai/models/phishing_behavior_model.pkl` and `.json` metadata: version `rf-synthetic-v2`, features, status `experimental`).
Evaluate: `python -m ai.evaluate_splits` (also reachable as `python -m ai.evaluate_model`).
Calibration comparison: `python -m ai.calibration_experiment`.

The old random 80/20 row split was replaced because rows of the same employee appeared on both sides. Two questions are now answered separately:

1. **Known employees, later simulations** — train on each employee's first 80%, test on the last 20%.
2. **Unseen employees** — `GroupKFold` by `employee_id`.

Results on the 2,400-row synthetic dataset (single run; differences below ~0.03 AUC are within noise):

| | Known employees | Unseen employees |
|---|---|---|
| Constant-rate baseline AUC | 0.500 | 0.500 |
| Employee past-click-rate baseline AUC | 0.583 | 0.519 |
| **Random Forest AUC** | **0.699** | **0.624** |
| Ceiling AUC (hidden generator probability, evaluation only) | 0.739 | 0.720 |
| Brier score: model / constant baseline | 0.175 / 0.199 | 0.187 / 0.195 |
| Click recall / precision at threshold = base rate | 0.62 / 0.41 | 0.58 / 0.36 |

History: with 50 simulations per employee the model was at chance level (AUC 0.56 / 0.50). The earlier 55.8% accuracy came from a random row split and should not be quoted. Configuration choice (no `class_weight`, `min_samples_leaf=10`) came from the calibration experiment: the previous `class_weight="balanced"` setting inflated probabilities (mean predicted 0.40 vs 0.27 observed; Brier worse than the constant baseline).

## 5. Model limitations

* Synthetic data from our own rules, 12 employee profiles: the model can at best recover those rules.
* Even a perfect model is limited here (ceiling AUC about 0.72-0.74).
* Precision at the chosen threshold is about 0.4: most flagged cases are not clicks. Use probabilities for ranking and as weak evidence, not as verdicts.
* Calibration was checked only on synthetic data.
* The saved model must not be evaluated on the CSV it was trained on.
* Not a substitute for real-data validation, drift monitoring or fairness review.

## 6. Agent decision workflow

1. Backend loads the employee's history (real data by default) and training status, and passes plain records to the agent.
2. Agent validates candidates (only the 12 approved scenarios).
3. Tool call: statistical analysis per scenario (counts, smoothed rate, Wilson interval, evidence level) plus the ML probability when available (blended 50/50; the weight is an untuned assumption). If the model is unavailable the agent continues on statistics alone and says so.
4. Policy:
   * **Cold start** (fewer than 5 simulations): baseline simulation of the least-tried scenario, easy difficulty, no weakness or training claims.
   * Otherwise pick the scenario with the highest `risk + 0.25 x interval width` (likely weakness *or* informative uncertainty). Never repeat the previous scenario back-to-back; skip scenarios with assigned-but-unfinished training.
   * **Weakness** needs at least 3 attempts, 2 clicks and estimated risk of at least 0.40 -> awareness training is recommended (a refresher if earlier training was completed).
   * Difficulty (easy / medium / hard) comes from the smoothed overall click rate. It is an advisory label; templates do not vary by difficulty yet.
5. Output: structured decision with mode, confidence (never "high"), rationale, guardrails applied, limitations, per-scenario assessments and model version.
6. The backend validates and, only after `confirm=true`, executes: creates a `Simulation` in campaign `AI Adaptive Simulations`, an audit `Event` (`agent_decision`), and, if recommended and not already open, a `Training` with 2 questions from the catalog.
7. Clicks and reports are recorded by existing/new tracking endpoints and appear in the next analysis.

Why it is "agent-like": it observes, calls tools, weighs evidence and uncertainty, chooses an action toward a goal and explains it. It does **not** learn by itself: it adapts because new recorded outcomes change what it observes. No LLM is used. If one is added later it should only phrase explanations from the structured decision and must never run SQL, read secrets, invent history or bypass the backend.

Not punitive by design: decisions are proposals requiring approval; training is supportive; one adaptive simulation per employee per 24 hours.

## 7. API (new endpoints; existing ones unchanged)

| Method and path | Purpose |
|---|---|
| `GET /ai/model-status` | Whether the model is loaded, version, status |
| `GET /employees/{id}/scenario-analysis?scenarios=a,b&include_synthetic=false&use_model=true` | Per-scenario evidence and estimates |
| `GET /employees/{id}/scenarios/{scenario}/click-probability` | Model probability for one scenario (503 if model missing) |
| `POST /employees/{id}/agent/decision` | Proposal only, no side effects |
| `POST /employees/{id}/agent/execute` | Re-runs the agent server-side; needs `confirm: true`, `approved_by`; optional `expected_scenario`; 409 on stale proposal or within cooldown |
| `GET /employees/{id}/agent/audit` | Executed decisions with rationale |
| `POST /simulations/{id}/report` | Record that the employee reported the email (idempotent) |

Changes to existing code: `backend/app/main.py` now includes the router and imports `text` (the `/db-test` endpoint used it without importing it). Responses contain employee ids only (no names, emails or password hashes). Errors use proper status codes (404, 409, 422, 503).

## 8. Running on Windows (PowerShell, project root, venv active)

```powershell
# Backend (main.py imports both `backend.*` and `app.*`, so both folders must be on the path)
$env:PYTHONPATH = ".;backend"
uvicorn app.main:app --reload

# Regenerate synthetic data, features, model, evaluation
python -m ai.data_generation.generate_training_data
python -m ai.feature_engineering
python -m ai.train_model
python -m ai.evaluate_splits

# Tests (use SQLite in memory; never touch PostgreSQL)
python -m pytest
```

Run scripts with `python -m ...` from the project root; running `python ai/xyz.py` fails because the project root is not on the import path.

## 10. Remaining limitations and next steps

* The agent/AI endpoints now require the admin token (see [ADMIN_PORTAL.md](ADMIN_PORTAL.md)); the rest of the pre-existing API (`/employees`, `/trainings`, ...) is still unauthenticated. `approved_by` on `agent/execute` is a free-text label.
* Model is experimental, synthetic-only; blend weight, thresholds and smoothing constants are documented assumptions, not tuned values.
* Difficulty does not yet change the email content.
* Training content is a short built-in catalog (2 questions per scenario).
* Simulation "sent" is a database record; this phase does not deliver real email.
* Agent decisions are not scheduled automatically; an administrator triggers them.
* Possible later work: collect real consented data, validate and recalibrate, add admin auth, scheduling, difficulty-specific templates, optional LLM for explanation text only.
* Housekeeping: `/employees/{id}/risk` (rule-based) still exists beside the new analysis; `main.py` mixes `backend.app` and `app` import roots; the model binary, its metadata and the feature CSV are generated files and are git-ignored (recreate them with the commands in section 8).
